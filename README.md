# Pulse Doppler DSP Chain on a PYNQ-Z2

Samples go in from an ADC, and it tells you what frequency the strongest signal
is sitting at and how far it stands above the noise, in dB.

## At a glance

| | |
|---|---|
| **What it does** | Runs a 64 point FFT over a stream of 12 bit ADC samples, then finds the strongest frequency bin and measures its signal to noise ratio |
| **Target** | PYNQ-Z2 board, Zynq `xc7z020clg400-1` |
| **Written in** | Verilog for the design, SystemVerilog for the testbench |
| **FFT** | Xilinx xfft 9.1, 64 point, natural order, scaled. Generated by `build.tcl`, not checked in |
| **Clock** | 125 MHz, closes with 0.932 ns of setup slack |
| **Size** | 1877 LUTs (3.5%), 3017 flip flops (2.8%), 8 DSP48s, half a block RAM |
| **Output rate** | One result per frame of 64 samples, with a short gap between frames (see [known limitations](#known-limitations)) |
| **Verified** | Self checking testbench passes, synthesis clean, timing met |
| **Not done** | Never run on real hardware, simulation and synthesis only |
| **Needs** | Vivado 2024.2 |
| **License** | MIT |

The idea is the front end of a pulse doppler radar receiver. Once you have the
spectrum of a burst of returns, the bin the peak lands in tells you the doppler
shift (so the target velocity) and the SNR tells you how much you can trust it.

I mostly built this because I wanted to actually build my own PD radar, so this
was the first natural step for me since im interested in fpga, unfortunately I
was blocked by strict RF regulation which made it complex and expensive to
actually make one.... maybe some day. Some things in here can probably be done
better and I have put what I would change at the bottom.

Everything here has been checked in simulation and through synthesis. I have
not had it running on the actual board yet, mostly because the ADC pin mapping
depends on which converter you hang off the headers (see
[xdc/pynq_z2.xdc](xdc/pynq_z2.xdc)).

## How it works

```
  adc_in[11:0]     +---------------+     +-----------+     +-----------------+     +-------------------+
  sample_valid --> | sample_buffer | --> | fft_block | --> | power_estimator | --> | snr_peak_detector |
                   |    64 x 12    |     | xfft 9.1  |     |  re^2 + im^2    |     |  peak, noise, dB  |
                   +---------------+     +-----------+     +-----------------+     +-------------------+
                     collect a frame       64 pt FFT         power per bin           peak_bin
                     then hold it          natural order     32 bit                  peak_bin_power_db
                                                                                     snr_db
                                                                                     result_valid
```

One frame of 64 samples goes in and one set of results comes out, with
`result_valid` high for a single clock when they update.

Following one result the whole way through:

1. **Collect.** `sample_buffer` takes 64 samples off the ADC into a small LUT
   RAM. Once it has a whole frame it raises `frame_ready` and stops accepting
   new ones, so the frame cannot get overwritten while it is being read out.
2. **Feed the FFT.** `fft_block` walks the buffer and pushes all 64 samples into
   the Xilinx core over AXI-Stream, pausing whenever the core drops `tready`.
   Each 12 bit sample is shifted up to sit at the top of the core's 16 bit input
   so the full range gets used, and the imaginary input is tied to zero because
   the ADC gives real samples rather than I and Q.
3. **Power per bin.** The core streams 64 complex bins back out. Two clocks
   behind it, `power_estimator` gives `re^2 + im^2` for each one.
4. **Peak and noise.** `snr_peak_detector` keeps the biggest bin and a running
   total as the frame goes past. At the end of the frame the noise floor is the
   total minus the peak, divided by the number of bins, and the SNR is those two
   numbers converted to dB and subtracted.
5. **Out.** `peak_bin`, `peak_bin_power_db` and `snr_db` all update together with
   `result_valid` high for one clock, then it starts on the next frame.

| Module | File | Job |
|---|---|---|
| `sample_buffer` | [rtl/sample_buffer.v](rtl/sample_buffer.v) | Collects 64 ADC samples into a small LUT RAM and holds them still while they are read out |
| `fft_block` | [rtl/fft_block.v](rtl/fft_block.v) | AXI-Stream wrapper for the Xilinx FFT core, sends the config word and streams the frame in |
| `power_estimator` | [rtl/power_estimator.v](rtl/power_estimator.v) | Two stage pipeline doing `re^2 + im^2` per bin |
| `snr_peak_detector` | [rtl/snr_peak_detector.v](rtl/snr_peak_detector.v) | Finds the peak bin, estimates the noise floor, converts both to dB |
| `pulse_doppler_dsp_top` | [rtl/top.v](rtl/top.v) | Wires the four together |

## Building it

You need Vivado 2024.2. The Vivado project is not in the repo because it is all
generated output, so build it from the script:

```bash
vivado -mode batch -source build.tcl
```

That creates `build/dsp_fft/` and generates the FFT IP with the right settings.
To create it and run the testbench in one go:

```bash
vivado -mode batch -source build.tcl -tclargs sim
```

Or to synthesise and get utilisation and timing reports in `build/`:

```bash
vivado -mode batch -source build.tcl -tclargs synth
```

If you would rather poke around in the GUI, run the first command and then open
`build/dsp_fft/dsp_fft.xpr`.

## The testbench

[sim/tb_pulse_doppler_dsp_top.sv](sim/tb_pulse_doppler_dsp_top.sv) builds a fake
ADC stream and checks the results itself. The tone frequencies are picked to sit
exactly on a bin centre so there is no leakage into the neighbouring bins, which
keeps the expected numbers clean and easy to reason about.

Three cases:

1. A clean tone in bin 7 with no noise, so the peak search and the bin numbering
   can be checked with nothing in the way.
2. The same tone in bin 20 with uniform noise of about +/-200 LSB against a 1000
   LSB tone, which is roughly 16 dB in the time domain.
3. Noise on its own with no target at all.

What it prints:

```
=== pulse doppler dsp chain, 64 point fft ===

  clean tone in bin 7
    peak bin        : 7
    peak power      : 71 dB
    snr             : 71 dB
    pass

  tone in bin 20 plus noise
    peak bin        : 20
    peak power      : 71 dB
    snr             : 30 dB
    pass

  noise only, no target
    peak bin        : 27
    peak power      : 46 dB
    snr             : 5 dB
    pass

=== all checks passed ===
```

Those all line up with what you would expect on paper, which was a nice moment
after a lot of staring at waveforms:

- Case 1 is limited by 12 bit quantisation plus whatever the FFT rounds off, and
  it comes out in the low 70s.
- Case 2 should be about 16 dB in the time domain plus roughly 15 dB of
  processing gain from spreading the noise across the 32 bins we look at, so
  around 31 dB. It reads 30.
- Case 3 is just the luckiest of 32 noise bins, which theory says sits about 6
  dB above the average. It reads 5.

## Design notes

A few things in here are not obvious, so it is worth writing down why they are
the way they are.

**The spectrum is mirrored, and that matters.** `fft_block` ties the imaginary
input to zero because the ADC gives real samples. That means the output spectrum
is symmetric: a tone in bin `k` also shows up in bin `64-k` with exactly the same
power. My first working version averaged all 64 bins to get the noise floor, and
the SNR was stuck at about 18 dB no matter how clean I made the input. The mirror
image of the target was being counted as noise. So `snr_peak_detector` only looks
at bins 1 to 32, which is the positive half. Bin 0 is skipped too, otherwise any
DC offset on the ADC wins the peak search every time.

**Noise floor is total minus peak.** The obvious way to seperate signal from
noise is to compare each bin against the running maximum and throw the losers
into a noise accumulator. That does not actually work. Once a big peak has been
found every later bin goes into the noise including any second real target, and
any early bin that happened to be the running maximum never gets counted as noise
at all. Adding everything up and subtracting the peak at the end avoids both
problems and is less logic anyway.

**Scaling schedule.** The FFT core is set to `scaled`, and `fft_block` writes one
config word after reset to pick the schedule. It shifts by 3 in the first pair of
radix 2 stages and 2 in each pair after, which is what Xilinx recommend in PG109
for the largest output that still cannot overflow. I got the bit layout of that
config word from the demo testbench the IP generates for itself rather than
trusting my reading of the datasheet, which saved me a while.

**dB without a log.** `10*log10(x)` is the same as `3.0103*log2(x)`, and log2 is
cheap: find the top set bit for the whole part, then take the four bits under it
as a straight line guess at the fraction. Because log2 is a curve and a straight
line under it always undershoots, the answer comes out slightly low, worst case
about a quarter of a dB. Some of that cancels out anyway because SNR is a
difference of two logs. The final scale by 3.0103/16 is done as `771/4096`, and
written as shifts and adds rather than a multiply, for the reason below.

**A DSP48 quietly ate my pipeline register.** This one took a while. The dB
conversion is split over two clocks so the priority encoder and the scaling are
not sat in one long path. It still missed 125 MHz by 133 ps. The timing report
pointed at a path ending on a DSP48 input pin, which was the giveaway: Vivado had
inferred a DSP for the `* 771`, then packed my pipeline register into the DSP's
own input register stage. That removed the fabric register I had deliberately put
there and left the log2 encoder driving straight into the DSP across a long
route. Writing the constant multiply out as shifts and adds keeps it in LUTs, the
register stays where I put it, and it closes with 0.932 ns spare. It also freed
up two DSPs.

## Bugs I had to fix to get this working

Keeping this list because most of it was not obvious and I would make the same
mistakes again otherwise.

The two that stopped it building at all:

1. The wrapper connected `.aresetn(rst_n)` on the FFT core, but `CONFIG.aresetn`
   was left at its default of `false`, so that port did not exist. Straight
   elaboration error.
2. The checked in `.xci` asked for a **1024** point transform, with bit reversed
   output ordering and truncation instead of rounding. Every one of those is
   just the IP's default, so the core had been dropped into the project and
   never actually configured, while all the RTL around it was written for 64
   points. Nothing lined up. This is the main reason `build.tcl` now generates
   the IP with every setting spelled out rather than trusting a saved `.xci`,
   because a `.xci` sitting on defaults looks exactly like a `.xci` somebody
   meant to write.

Then the ones that would have given wrong answers:

3. `m_axis_data_tready` was not connected, so it floated and the core never let
   any output through.
4. `s_axis_data_tready` was ignored completely. The core is set to the Non Real
   Time throttle scheme, which means it is allowed to drop ready and expects you
   to hold off.
5. `sample_buffer` never actually streamed the frame out. It drove
   `buffer[wr_ptr]`, which is the location being *written*, so the FFT got the
   same sample 64 times over. There is a read address and a proper handshake now.
6. The 12 bit buffer output was wired onto a 16 bit bus with no sign extension,
   so every negative sample turned into a large positive one. It now gets shifted
   up so the sign bit lands in bit 15, which also makes better use of the core's
   range.
7. `buffer_ready` latched high and never cleared, and the buffer carried on
   overwriting itself while it was being read.
8. `s_axis_data_tvalid` and `tlast` were only ever assigned inside the send
   state and never cleared, so both stuck high after the frame finished.
9. `power_estimator` had two clocks of latency but only delayed `valid` by one,
   so the peak detector was looking at the wrong bin the whole way through.
10. The frame end maths in `snr_peak_detector` read the `max_power` register with
    a blocking assignment before the non blocking update had landed, so the last
    bin of every frame never counted.
11. `noise_sum / (N-1)` inferred a 32 bit divide by 63. It is a shift now, and
    dividing by 32 instead of 31 only costs about 0.14 dB.
12. `snr_db` was unsigned, so a negative SNR wrapped round to about 65535.
13. There was no constraints file and no testbench, so there was nothing to run
    and no clock defined.
14. There was a stray unicode character in one of the comments in
    `snr_peak_detector.v`, which some tools are not happy about.

## Known limitations

Things I know are not great, in case anyone reads this and wonders whether I
noticed. What I would actually do about them is in the next section.

- **Samples get dropped between frames.** The buffer stops accepting while a
  frame is being read out, so a handful of samples are lost each time. Every
  frame is still 64 consecutive samples so the maths is fine, but it is a
  snapshot rather than a continuous spectrogram.
- **Real input only.** The imaginary side is tied to zero, so half the spectrum
  is just a mirror of the other half and gets thrown away. It also means there
  is no way to tell a target closing from one opening, because a doppler shift
  up and the same shift down land in the same place.
- **No window function.** Anything not sat exactly on a bin centre smears into
  its neighbours and reads a few dB worse than it should. My testbench tones are
  deliberately on bin centres, so the numbers it prints are the best case rather
  than a typical one.
- **The peak search always finds something.** There is no threshold, so the
  biggest bin wins even when the frame is pure noise. That is exactly why the
  noise only test still reports a peak in bin 27. It cannot say "nothing there".
- **No overflow flag.** `CONFIG.ovflo` is off, so I am trusting the scaling
  schedule rather than actually knowing it never overflows.
- **The results do not go anywhere yet.** The outputs come to 39 bits, which is
  more than the board has spare pins for, so right now they just sit at the top
  level with nothing reading them.
- **Not tested on hardware.** Simulation and synthesis only so far.

## Improvements I want to make

Roughly in the order I would do them. The first few are small and I know how to
do them, the later ones are proper pieces of work.

**1. Ping pong the sample buffer.** Two 64 sample buffers instead of one, filling
one while the other streams into the FFT. This is the change that turns it from a
snapshot into something that could run continuously, and it is the easiest win on
this list. `sample_buffer` needs one extra address bit and a flag to say which
half is which, and `fft_block` would not have to change at all because it already
goes through a proper handshake.

**2. Bring the overflow flag out.** Switch `CONFIG.ovflo` on in `build.tcl` and
route `event_fft_overflow` up to the top level. Nearly free, and then I actually
know the scaling schedule is holding instead of assuming it.

**3. A window function.** A Hann window on the way into the FFT. The window is
symmetric so a 32 entry ROM covers all 64 coefficients, plus one multiplier in
the path between the buffer and `fft_block`. Right now my testbench only ever
uses tones sat exactly on a bin centre, which quietly flatters the SNR numbers.
Anything real would not be that tidy.

**4. CFAR instead of a plain peak search.** At the moment the largest bin always
wins, which is why the noise only test still points at bin 27. Cell averaging
CFAR sets the threshold from the bins around the one under test and only declares
a detection if it clears it by some margin. That is the difference between "the
biggest bin is 27" and "there is genuinely a target in bin 27", which is the
thing you actually want from a radar. It needs a sliding window sum across the
bins, so it is a decent chunk of logic but not conceptually hard.

**5. AXI-Lite registers so the PS can read the results.** This is the whole point
of using a Zynq rather than a plain FPGA, and it annoys me that it is not done
yet. Peak bin, peak power, SNR and a frame counter in a handful of read only
registers, wired to the PS through the AXI interconnect, then a short Python
script on the ARM side to poll them and plot. Biggest single job here.

**6. I/Q input.** Feed the imaginary side properly instead of grounding it. That
doubles the useful bins from 32 to 64 and gives the sign of the doppler shift, so
you can finally tell a closing target from an opening one. Partly a hardware
problem though, since it needs a second ADC channel and a quadrature downmix in
front of it.

**7. A longer transform.** 64 bins is coarse for doppler resolution. Going to 256
or 1024 is mostly just `CONFIG.transform_length` and the `N` parameter, but the
scaling schedule in `fft_block.v` is hardcoded as three stage pairs for 64
points, so that would need generating from `N` rather than written out by hand.
Worth doing properly rather than hardcoding a second magic number.

**8. Get it onto the actual board.** Needs the ADC pins pinned down in the XDC
first, which is waiting on me picking a converter.
